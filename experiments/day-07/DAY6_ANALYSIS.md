## Состав v3

Train: **420** = 60 простых шаблонных + 120 сохранённых пограничных/мобильных + 240 новых контрастных.
Valid: **137** = прежние 65 + 72 новых контрастных.
Final eval: **140**, неизменный. Mobile eval: прежние 40 из этих 140, тоже неизменные.

Контрастные примеры составляют 60 train-групп и 18 valid-групп по четыре. Шесть направлений: direction, currency, amount, date, context, precision. Все варианты семейства находятся в одном наборе. Для valid используются другие предметы покупок и формулировки. Точные темы/предметы могут семантически пересекаться с другими примерами: полная независимость смысловых классов не требуется и не заявляется.

В train оставлены целые старые лексические семейства, по шесть обычных примеров каждой категории. 180 однотипных строк удалены из активного train, но сохранены в архиве v2. Данные не размножались до условной цели 2048 повторением строк.

**Ограничение:** 240 новых примеров тоже строятся контролируемыми шаблонами из ограниченного словаря. Их отличие — содержательно значимые контрасты, а не независимое естественное разнообразие. Доля всех шаблонно созданных примеров не объявляется уменьшившейся. Цены синтетические. Четыре связанных примера не равны четырём независимым наблюдениям; для bootstrap на новом valid единица ресэмплинга — семейство.

## Следующее обучение: обязательные условия

1. Начинать от исходных весов Qwen, **не от detox-адаптера Day 6**. Сначала baseline с тем же system.txt; сохранять ответы и точные параметры генерации.
2. Сохранить mask_prompt=true, официальный шаблон и max_seq_length=2048. Не переносить 256 токенов из Day 6.
3. Если используется прежний MLX-LM 0.32.2, подключить проверенный `day-06/loss.py::completion_loss` и повторить проверку padding на конфигурации нового runner. В этой задаче runner обучения Day 7 не создавался.
4. Сделать короткий pilot на длинных примерах. В v2 было до 1272 токенов вместо типичных ~86 в Day 6; исключение промпта из loss не убирает его вычислительную стоимость. Длинный system-промпт сейчас намеренно сохранён ради неизменной финальной проверки; его сокращение — отдельный контролируемый эксперимент.
5. Число эпох считать по реальным примерам/optimizer updates, не копировать 2048 микрошагов автоматически. Checkpoint выбирать по valid-генерациям; loss — диагностический показатель.
6. Сравнивать полный exact match, количество ухудшений, ошибки важных полей и ложные расходы. Не объявлять улучшением вариант, у которого вырос общий балл, но стало больше опасных ложных записей. Повторить выбранный режим с другим seed.
7. После выбора конфигурации один раз открыть итоговые ответы eval. Не использовать результаты финального eval для дописывания train. Для проверки превосходства именно v3 над v2 потребуется отдельное контролируемое обучение обоих наборов с одинаковым бюджетом optimizer updates/экспозиций, зафиксировав выбранный способ выравнивания.

## Инструмент оценки

`score_candidates.py` принимает provenance и сохранённые ответы `{"id":"…","response":"{…}"}` в JSONL. Не запускает модель. Проверяет полный набор уникальных ID, считает полный exact match, правильность отдельных полей, срезы статусов/категорий/mobile/контрастов и целиком пройденные группы. С --baseline возвращает ID улучшений и регрессий.

```sh
python3 experiments/day-07/score_candidates.py \
  --references experiments/day-07/data/valid_provenance.jsonl \
  --predictions /path/to/tuned-valid.jsonl \
  --baseline /path/to/base-valid.jsonl
```

Это инструмент для будущих измерений. Его unit-тесты на искусственных ответах не являются оценкой качества Qwen. Поля null на ignored легко повышают частичную точность; основной результат — полный exact match со срезами и перечнем ошибок.
