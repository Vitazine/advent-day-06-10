## Формат

Train/valid — одна запись `{"messages":[system,user,assistant]}` на строку, совместимая с ChatDataset. Есть обычные краткие ответы и запросы JSON `{"answer":"...","status":"known"}`. Для неуказанных в книгах сведений: `{"answer":null,"status":"not_specified"}`. Исправления ложных предпосылок отвечают прямо, с корректным фактом.

Eval-файлы содержат только `id` и `messages` из system/user. Эталоны вынесены в соответствующие `*_references.jsonl`; у final — в `final_provenance.jsonl`. Не передавать эти эталоны в генерацию, кроме **явного** oracle-context сравнения по протоколу. Файлы format/style уже содержат необходимый фактический контекст по замыслу теста.

`facts_seed.txt` — вручную составленные вопрос/ответ/переформулировка и книжный locator. `style_seed.txt` — отдельно написанные разговорные заметки. `build_dataset.py` собирает JSONL без модели, сети и случайной генерации фактов. `facts.jsonl` связывает каждый пример с источником; через provenance можно восстановить его карточки. Метаданные источников не расходуют токены обучения.

Даты не являются ISO-датами нашей истории: сохраняются эпоха и точность, например «около 1600 года Второй эпохи». Неуказанные плотность митрила, размер Кольца и точные рецепты не выдумываются. Отсутствующие сведения ограничиваются выбранными книгами, не всем наследием Толкина.

## Совместимость и скорость

Проверены все 376 train/valid-примеров локальным токенизатором Qwen и `ChatDataset(mask_prompt=True)`: длины **133–244 токена**, средняя **174,1**, p95 **214**. Максимум ответа с завершающими токенами — **56**. Ни один ответ не обрезается при `max_seq_length=256`. Генерация eval — отдельный бюджет до 128 новых токенов; размер обучающей последовательности не является ограничением контекста инференса.

**Обязательно явно подменять chat template на локальный `chat_template.jinja` и при обучении, и при генерации.** Он побайтово совпадает с одобренным non-thinking-шаблоном Day 6 (`64f85b…9c326`). В папке исходной модели обнаружен thinking-шаблон, добавляющий `<think>`; автоматическое использование его по умолчанию не соответствует этому корпусу. Папка модели не менялась. Проверены совпадение train/generation-префикса, начало assistant-loss и настоящий завершающий `<|im_end|>`.

Профиль: QLoRA q/v, последние 16 слоёв, rank16, MLX scale2, batch1, accumulation4, LR1e-4, 2 эпохи. Это **704 микрошагa / 176 optimizer updates**, не 704 обновления. При необходимости поздний checkpoint — до четырёх эпох, только если pilot и бюджет позволяют. Профиль JSON — инструкция для будущего runner, не готовая команда обучения. Нужно подключить исправленный `day-06/loss.py::completion_loss`; этот датасет сам не меняет библиотечный loss.

В Day 6 2048 коротких примеров занимали 26–51 минуту, а в Day 7 420 последовательностей длиной около 1200 токенов — 101–113 минут. Поэтому здесь короткий system и ответы. Перенос времени между задачами не гарантирован: сначала pilot (10 прогревочных + 50 измеряемых микрошагов), затем прогноз с полной валидацией и генерациями. Резерв на оценку — 60 минут, предел основной тренировки — 100 минут. Повторный seed и широкий перебор конфигураций в этот бюджет не включены.

## Проверки и воспроизведение

Без MLX и загрузки весов (Python 3.9+):

```sh
python3 -m unittest discover -s experiments/day-08 -p 'test_*.py'
python3 experiments/day-08/verify_dataset.py
```

Токенизация в существующем окружении, без загрузки весов:

```sh
HF_HUB_OFFLINE=1 python3 experiments/day-08/verify_dataset.py --tokenizer
```

Импорт MLX требует доступного Metal даже для этой проверки. В песочнице первоначальный импорт завершился `No Metal device available`; полный повтор с доступом к Metal прошёл. Для обычной структурной проверки GPU не нужен. Флаг `--report` явно задаёт путь отчёта; запуск без него не затирает сохранённую GPU-проверку.

Сборка новой копии:

```sh
python3 experiments/day-08/build_dataset.py --output /tmp/day08-rebuild
```

Каталог должен быть пустым. Генератор отказывается перезаписывать существующий датасет. Проверка сама собирает временную копию и сравнивает все хеши, включая manifest. После baseline изменения требуют новой версии, нового manifest и нового final; нельзя подправлять train по ответам final.

## Перенесённые практики Day 6/7 и ограничения

Сохранены assistant-only loss, non-thinking-шаблон, контроль токенов, контрасты, provenance, фиксация хешей и выбор по dev-генерациям. Тесты проверяют разделение групп, отсутствие эталонов в eval messages, правильную эпоху/приблизительность, новые формулировки и регрессии найденных ошибок.

Намеренное пересечение фактов train и knowledge-eval нужно для Day 8. Holdout valid/final содержит новые целевые факты, но не обязательно полностью новые имена. Проверки нормализованных дубликатов и групп не являются доказательством полной семантической независимости. Вопросы вручную написаны, но JSON-обёртки шаблонные; это не реальные пользовательские запросы.

Источники — книжные адреса и вторичные справочные сверки; полный аудит по первичным текстам и человеком не выполнен. Все карточки просмотрены автором, исходный корпус прошёл отдельное AI-ревью, три существенных замечания исправлены. Малые holdout и особенно style (6 final) подходят для учебной демонстрации; сильные статистические выводы по ним не обоснованы.

Ни неизвестность этих фактов базе, ни прирост знаний, ни отсутствие регрессий, ни время 2–3 часа пока не измерены. `baseline_knowledge=not_measured` сохранено явно. Следующая стадия — baseline и pilot по отдельному запросу пользователя.
