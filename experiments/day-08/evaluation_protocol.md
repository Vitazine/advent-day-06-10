# Day 8: протокол измерений до начала обучения

## Сначала baseline

1. Проверить manifest, токенизатор, non-thinking-шаблон. Загрузить исходную Qwen3-4B-Instruct-2507-4bit без адаптеров Day 6/7.
2. Прогнать `baseline_screen.jsonl` (140 исходных вопросов) и `knowledge_dev.jsonl`. Сохранить ответы, seed, параметры, версии и хеши. Не передавать в генератор файлы references/provenance или facts целиком.
3. На screen отметить `correct / wrong / unsupported / ambiguous` по рубрике. Срез «неизвестно базе» означает лишь провал этого baseline при выбранном decoding; это не доказательство отсутствия знания в весах. Ошибка на original и успех на парафразе также возможны.
4. Не изменять зафиксированный train под ответы на final. Если на screen не окажется ошибок, честно признать, что текущий набор не проверяет усвоение новых для базы знаний. Следующая версия потребует новых проверенных фактов и нового закрытого final.

## Сравнения

| Режим | Веса | Вход |
|---|---|---|
| base | исходные | system.txt + вопрос |
| prompt | исходные | улучшенный промпт, выбранный только на dev |
| oracle-context | исходные | тот же вопрос + короткий истинный факт из references.context |
| tuned | выбранный адаптер | точно тот же system.txt + вопрос, что base |

Для знания основной вопрос — `knowledge_final`: новая формулировка обученного факта. `recall_final` — исходный обучающий вопрос к тем же фактам; сравнивать попарно, не складывать как независимые наблюдения. `final.jsonl` — другие целевые факты, отсутствующие в обучении; это контроль сохранения/переноса, а не тест запоминания неизвестного материала. В нём остаются известные имена, но целевые отношения не должны попадать в train. Строгой независимости всех сущностей или полной семантической независимости не заявляем.

Oracle-context — верхняя оценка помощи правильного контекста, **не измерение реального RAG**: поиск, ранжирование, ошибки извлечения и стоимость индекса здесь отсутствуют. Данные, память, промпт и формат ответа не менять одновременно между base и tuned.

Для format/style сравнивать base, улучшенный prompt и tuned на одних и тех же входах с предоставленным контекстом. Это отделяет следование формату и тон от памяти. Срез brevity вспомогательный, не заменяет style.

Условия генерации: temperature=0, max_tokens=128, один и тот же chat_template.jinja. Это воспроизводимый экспериментальный decoding, не заявление об оптимальных пользовательских настройках. При обрезании ответа помечать truncated; изменение лимита требует одинакового повторного прогона всех сравниваемых режимов. Для general применять его собственный нейтральный system, не доменный.

## Рубрика

**Факты (0/1):** правильный ответ на заданный вопрос, без противоречащих и выдуманных дополнений. Допускать падежи и признанные варианты перевода имён. Нельзя сравнивать только подстроку: «не Бард» содержит «Бард», но неверно. Для даты обязательны правильный год, эпоха, а для точного вопроса также день/месяц. Приблизительную дату нельзя выдавать за точную. Ответ на вопрос «кто?» должен называть лицо, а не соответствующий предмет. Отдельно считать отказы/неуверенность и ошибки. Субъективные ответы проверить вслепую по перемешанным base/tuned-парам; для значимых выводов нужен человек. Сохранить причины разметки.

**Неизвестное:** `robustness_final` содержит новые формулировки обученных контрастов и неизвестных сведений. Отсутствие даты рождения Леголаса не означает отсутствие всей информации о Леголасе. Оценивать отсутствие выдумки и правильное ограничение ответа выбранными книгами. Этот набор не проверяет универсальную калибровку на совершенно новых типах неизвестного.

**Формат:** разобрать ровно один JSON без оград Markdown и внешнего текста; запретить повторные ключи; ровно answer/status. status из known/not_specified, answer строка для known и null для not_specified. Сообщать отдельно (а) валидность схемы, (б) смысловую правильность answer/status. Порядок ключей и пробелы несущественны. Пустая строка не заменяет null. Контекст содержит ответ намеренно: здесь измеряется оформление.

**Стиль:** отдельные баллы 0/1 за нейтральный тон, отсутствие разговорных наполнителей, краткость (не более двух предложений без вступлений), сохранение всех фактов и отсутствие новых утверждений. Основная доля успехов — все четыре условия одновременно. Не использовать точное строковое совпадение с примером target; это один допустимый пересказ. Всего 6 final-кейсов: по ним возможна только небольшая демонстрация, не сильное статистическое утверждение.

**Общие задачи:** 40 синтетических кейсов по 8 на арифметику, логику, язык, формат и извлечение. Для JSON — структурное равенство с точными типами, без повторных ключей. Для остальных — trim/Unicode NFC, точный результат с соблюдением явно запрошенного формата. Сохранять все регрессии base-pass/tuned-fail с исходными ответами, даже если общий балл вырос. Это небольшой простой smoke-набор, не общий benchmark модели.

## Выбор адаптера и переобучение

- Метрики train и valid вычислять одним исправленным assistant-only loss из Day 6, с одинаковым исключением padding. Не использовать дефектную границу default_loss старого MLX-LM.
- Сохранять checkpoint каждую половину эпохи. На всех checkpoint оценивать фиксированный valid и небольшой неизменный срез knowledge_dev; на кандидатах — весь knowledge_dev, format_valid, style_valid, robustness_dev.
- Выбор: сначала фактическая точность knowledge_dev, затем отсутствие галлюцинаций в robustness_dev, далее формат и стиль; при равенстве более ранний checkpoint. Не выбирать только по минимальному valid loss.
- Для наглядного графика сохранять train loss на фиксированном train-probe, не сравнивать шумный loss разных случайных батчей с full-valid как точные парные значения.
- Отдельно сохранить поздний checkpoint для диагностики: train loss снижается, valid loss устойчиво растёт/стоит, генерации на новых формулировках ухудшаются. Одного колебания valid недостаточно. Если переобучение за бюджет не проявилось — записать это, не дорисовывать эффект.
- Выбранный и диагностический поздний checkpoint зафиксировать хешами **до** final. После просмотра final параметры/данные не менять. Поздний checkpoint не подменяет выбранный.
- В статистике единица — группа фактов, а не QA/JSON-строка; отдельные группы также могут быть семантически связаны. Не складывать recall/knowledge, brevity/style и format/holdout как независимые тесты.

Итоговый отчёт должен показать отдельный прирост знаний, формата, стиля, регрессии общих задач, время обучения и генераций, память и наблюдавшееся/не наблюдавшееся переобучение. Время подготовки корпуса учитывается отдельно.
